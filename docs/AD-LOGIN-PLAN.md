### 1.3 ระบบล็อกอินปัจจุบัน (อ่านจากโค้ด)

- **NextAuth v4.24.13** (`^4.24.13`) + Credentials provider อย่างเดียว ใน [lib/auth.ts](../lib/auth.ts) เซสชันเป็น JWT อายุ 8 ชั่วโมง
- ตรวจรหัสผ่านกับ bcrypt ในคอลัมน์ `User.password` (มี SHA-256 เก่ารองรับและอัปเกรดตอนล็อกอิน) ปัจจุบันทุกบัญชีเป็น bcrypt
- **ทุก request ตรวจ `isActive` และ `role` จาก DB ซ้ำ** ([lib/api-auth.ts](../lib/api-auth.ts) `getAuthUser`) → ปิดบัญชีหรือเปลี่ยนบทบาทมีผลทันที คุณสมบัตินี้ต้องรักษาไว้
- `middleware.ts` ใช้ `token.roleName` และ `token.sub` — ต้องอยู่ใน Edge runtime ห้าม import Node/Prisma
- **ไม่มีการจำกัดอัตราการลองล็อกอินเลยในปัจจุบัน** (ตรวจแล้ว): `matcher` ของ middleware ไม่มี `/api/auth/*` จึงไม่ครอบ `POST /api/auth/callback/credentials` ซึ่งเป็นจุดตรวจรหัสผ่านจริง ตัวจำกัด (`lib/rate-limit.ts`) เป็นหน่วยความจำของโปรเซสเดียว และผู้ที่ยังไม่ล็อกอินทุกคนใช้บัคเก็ต `anonymous` ร่วมกัน (100 ครั้ง/นาที) → ถึงจะมาครอบ endpoint ล็อกอินก็ไม่พอ เพราะคนเดียวยิงจนเต็มได้ ทำให้ผู้ใช้จริงทุกคนถูก 429
  ปัญหานี้**มีอยู่แล้วกับระบบปัจจุบัน** (เดารหัสผ่านบัญชีในแอปได้ไม่จำกัด) แต่เมื่อใช้ AD ความเสียหายต่างกันมาก: รหัสผ่านที่เดาถูกคือรหัสผ่านโดเมนซึ่งพนักงานใช้กับระบบอื่นด้วย
- ผู้ใช้ผูกกับ role ผ่าน `User.roleId` และกับแผนกผ่าน `User.departmentId`; `username` ไม่ซ้ำ; `email` บังคับ
- ชื่อบทบาทใน DB สะสมความไม่สม่ำเสมอ (ดู `lib/auth-constants.ts`) — เป็นเจตนา ห้ามเก็บกวาด

**ข้อมูลในฐาน dev:** มีเฉพาะผู้ใช้ตัวอย่างจาก seed 11 บัญชี (`req_cane`, `head_cane`, …) อีเมล `@example.com` — **ไม่มีผู้ใช้จริงของบริษัท** ดังนั้นไม่มีงาน "ย้ายผู้ใช้เดิม" ให้ทำบนฐานนี้ ส่วนฐาน production ผมไม่ได้เข้าถึง จึงไม่ทราบว่ามีผู้ใช้จริงกี่คนและชื่อผู้ใช้เป็นแบบใด

## 2. ทางเลือกทางเทคนิค

| | ก. LDAP bind จากแอป (ผู้ใช้พิมพ์รหัสผ่านโดเมนในหน้าล็อกอินเดิม) | ข. SSO ผ่าน Kerberos/Windows (เข้าอัตโนมัติ) | ค. Entra ID (OIDC) |
|---|---|---|---|
| ผู้ใช้เห็นอะไร | หน้าล็อกอินเดิม ใช้ชื่อ/รหัสผ่านโดเมน | ไม่ต้องล็อกอิน | ปุ่ม "Sign in with Microsoft" |
| พอร์ตที่ต้องการ | 636 (LDAPS) — **เปิดแล้ว** | 88 + SPN + IIS/IISNode หรือ reverse proxy | ออกอินเทอร์เน็ตไป Microsoft |
| งานโครงสร้าง | ต่ำ | **สูง** — แอปรันบน Node/PM2 ไม่ใช่ IIS การทำ Windows Integrated Auth กับ Node ไม่ง่ายและเปราะ | ปานกลาง — ต้องลงทะเบียนแอปใน tenant, ผู้ดูแล Entra ต้องร่วม, ต้องยืนยันว่า AD ซิงก์ขึ้น Entra ครบ |
| ความเสี่ยงหลัก | แอปเห็นรหัสผ่านโดเมนของผู้ใช้ (ต้องใช้ LDAPS เท่านั้น ห้ามบันทึกลง log) | การตั้งค่าเปราะ | พึ่งบริการภายนอกและการซิงก์ |
| เข้ากับ NextAuth v4 | **ตรงที่สุด** — ใช้ Credentials provider เดิม เปลี่ยนแค่ `authorize` | ต้องเขียน provider เอง | มี provider สำเร็จรูป (`AzureADProvider`) |

**ข้อเสนอ: ทางเลือก ก (LDAPS bind)** เพราะพอร์ตเปิดอยู่แล้ว, เปลี่ยนน้อยที่สุด, ไม่เปลี่ยนรูปแบบเซสชัน/middleware/การตรวจ role ซ้ำต่อ request, และผู้ใช้ไม่เห็นความต่างมากนัก ข้อแลกเปลี่ยนที่ต้องยอมรับคือแอปได้รับรหัสผ่านโดเมนของผู้ใช้ — ลดความเสี่ยงด้วย LDAPS + ไม่ log + จำกัดอัตราการลอง
ข (SSO) น่าสนใจในแง่ประสบการณ์ผู้ใช้ แต่เป็นโครงการแยกและเสี่ยงกว่ามาก ควรพิจารณาทีหลังเมื่อ ก เสถียรแล้ว ไม่ควรรวมกัน

## 3. การตัดสินใจที่ต้องให้คนตัดสิน (ผมไม่ควรเดาแทน)

> แผนด้านล่างเขียนบนสมมติฐานที่ระบุไว้ในวงเล็บ แต่ละข้อเปลี่ยนงานจริง ถ้าคำตอบต่างจากสมมติฐานต้องกลับมาแก้แผน

1. **ใครเข้าระบบได้บ้าง?** *(สมมติฐาน: เฉพาะคนที่อยู่ในกลุ่ม AD ของแอปนี้)*
   - (ก) ทุกคนใน AD เข้าได้ ระบบสร้างบัญชีให้ตอนล็อกอินครั้งแรกเป็นบทบาท `User` — ง่าย แต่คนนอกกลุ่มงานก็เห็นระบบ
   - (ข) เฉพาะสมาชิกกลุ่ม AD ที่กำหนด (เช่น `G_RequestOnline`) — **ผมแนะนำ** เพราะองค์กรมีแบบแผนกลุ่ม `G_*` อยู่แล้ว และให้ผู้ดูแล AD คุมสิทธิ์เข้าแอป
   - (ค) ต้องให้ Admin สร้างบัญชีในแอปก่อน แล้ว AD ใช้ยืนยันตัวตนเท่านั้น — เข้มสุด แต่เพิ่มงาน Admin
2. **บทบาท (Admin / หัวหน้า / บัญชี / IT ฯลฯ) มาจากไหน?** *(สมมติฐาน: ยังเก็บใน DB และ Admin กำหนดที่หน้าผู้ใช้เหมือนเดิม; AD ใช้เพื่อยืนยันตัวตนและดึงชื่อ/อีเมลเท่านั้น)*
   - ทางเลือก: map กลุ่ม AD → บทบาท (เช่น `G_RequestOnline_Accountant`) ซึ่งสะดวกถ้าผู้ดูแล AD ยินดีดูแลกลุ่ม แต่ต้องกำหนดกฎเมื่อคนอยู่หลายกลุ่ม และเมื่อกลุ่มกับ DB ขัดกัน
   - เหตุที่ไม่แนะนำให้อนุมานจาก `department`/`title`: เป็นข้อความอิสระ ไม่น่าเชื่อถือ และเกี่ยวกับสิทธิ์อนุมัติเงิน
3. **ยังให้มีล็อกอินด้วยรหัสผ่านในแอปไว้หรือไม่?** *(สมมติฐาน: ให้ — เฉพาะบัญชีที่ Admin ติ๊ก "บัญชีภายใน" เช่น admin ฉุกเฉิน และบัญชีทดสอบ)*
   - จำเป็นอย่างน้อยสองเรื่อง: (1) ถ้า AD/เครือข่ายล่ม ต้องมีทางเข้า Admin ได้ (break-glass) (2) ชุด E2E 37 ข้อสร้างบัญชี `e2e_*` พร้อมรหัสผ่านและพึ่งมันทั้งชุด
   - ถ้าตอบ "ไม่ให้มีเลย" ต้องลงทุนทำทางเข้าฉุกเฉินและวิธีทดสอบแบบใหม่ทั้งหมด (งานใหญ่ขึ้นมาก)
4. **กลุ่ม AD ของแอปมีอยู่แล้วหรือยัง ใครสร้างได้?** (ผมเห็นเพียงว่ามี `G_AppTestAdmin`, `G_IT`, `G_Softpro` ของบัญชีผู้พัฒนา — ไม่รู้ว่าเป็นของแอปนี้หรือไม่)
5. **บัญชีบริการสำหรับค้นหาใน AD:** LDAPS bind ต้องมีบัญชีอ่านอย่างเดียว (หรือใช้ bind ด้วยตัวผู้ใช้เอง) ใครขอ/ดูแลรหัสผ่านบัญชีนี้ และเก็บที่ไหน (ตอนนี้ secret อยู่ใน `.env` เท่านั้น)
6. **โดเมนอีเมล:** `mail` เป็น `@tusm.thaisugarmill.com` แต่ UPN เป็น `@tusm.com` ยืนยันว่าอีเมลที่ใช้รับแจ้งเตือนคือค่า `mail` และทุกคนมีค่านี้หรือไม่ (ผมตรวจแค่ 1 บัญชี)
7. **ผู้ใช้ที่ AD ปิดบัญชี/ลาออก:** *(สมมติฐาน: ล็อกอินไม่ได้ทันทีเพราะ bind ไม่ผ่าน; ส่วนเซสชันที่ค้างอยู่ใช้ได้ถึง 8 ชั่วโมงเว้นแต่ Admin ปิด `isActive` ในแอป — ดูข้อ 4.5)*

## 4. แผนดำเนินการ (ตามสมมติฐานข้อเสนอ: LDAPS bind + สิทธิ์เข้าด้วยกลุ่ม AD + บทบาทเก็บใน DB + เก็บล็อกอิน local ไว้เฉพาะบัญชีภายใน)

### ระยะ 0 — เตรียมการและตัดสินใจ (ไม่แตะโค้ด)
- [ ] ตอบข้อ 1–7 ใน §3
- [ ] ตรวจจาก **เครื่อง production** ว่าเข้า `TUSMDC01/02` พอร์ต 636 ได้ และ certificate ของ DC เชื่อถือได้ (CA ภายในต้องอยู่ใน trust store ของ Node — มิฉะนั้นต้องตั้ง `NODE_EXTRA_CA_CERTS`) **อย่าปิดการตรวจ certificate**
- [ ] ขอบัญชีบริการอ่านอย่างเดียว (หรือยืนยันว่าใช้ user bind) และกลุ่ม AD ของแอป
- [ ] ตรวจนโยบาย LDAP signing/channel binding ของ DC (ผู้ดูแล AD) เพื่อให้ไลบรารีที่เลือกเข้ากันได้
- [ ] ดึงรายชื่อผู้ใช้จริง/กลุ่มที่จะให้เข้า เพื่อดูว่า `mail`, `department`, `title` ครบกี่ % (อย่าอนุมานจากบัญชีเดียว)

### ระยะ 1 — แกนล็อกอินด้วย AD (ฟีเจอร์เปิด/ปิดด้วย env ได้ ค่าเริ่มต้น = ปิด)
- [ ] เพิ่มคอลัมน์ใน `User`: **`authSource`** (`'LOCAL' | 'AD'`, ค่าเริ่มต้น `'LOCAL'` เพื่อไม่กระทบบัญชีเดิม) และ **`adObjectGuid`** (ตัวระบุถาวรของ AD ไม่เปลี่ยนแม้ชื่อผู้ใช้เปลี่ยน — ใช้ผูกบัญชีแทนการเทียบชื่อ) ผ่าน migration SQL ตามแบบแผนโปรเจกต์ (idempotent, ทดสอบบนสำเนาฐาน) และอัปเดต baseline/seed
- [ ] `lib/ad.ts` — แยก logic AD ออกจาก NextAuth เพื่อ unit test ได้: ค้นหา DN จาก `sAMAccountName`, bind ด้วยรหัสผ่านผู้ใช้, อ่าน `mail`/`displayName`/`title`/`department`/`objectGUID`/`memberOf`/`userAccountControl`, **escape ค่าที่ใส่ใน LDAP filter** (กัน LDAP injection) , timeout สั้น, failover DC01→DC02
- [ ] ปรับ `authorize()` ใน `lib/auth.ts`: ถ้าบัญชีเป็น `LOCAL` ตรวจ bcrypt เหมือนเดิม; ถ้าเป็น `AD` (หรือยังไม่มีบัญชีและเปิดโหมด AD) ตรวจกับ AD แล้วเช็คสมาชิกกลุ่มที่อนุญาต; **คงการตรวจ `isActive` และ role จาก DB ต่อ request ตามเดิม**
- [ ] ไลบรารี: ยังไม่ได้ติดตั้ง LDAP library ใดในโปรเจกต์ (ตรวจแล้ว) ต้องเลือกและประเมินก่อน (เช่น `ldapts` ซึ่งเป็น TypeScript และรองรับ LDAPS) — **ต้องทดสอบกับ DC จริงว่าทำงานบน Node 22 + Windows** ก่อนยึดเป็นทางเลือก ไม่ควรสรุปจากชื่อ
- [ ] **ห้าม log รหัสผ่านหรือ LDAP bind request** ทุกกรณี รวมถึงตอนเกิด error; ข้อความ error ที่ผู้ใช้เห็นต้องไม่เปิดเผยว่า "ไม่มีผู้ใช้" กับ "รหัสผ่านผิด" ต่างกัน
- [ ] **จำกัดอัตราการลองล็อกอิน — เป็นเงื่อนไขก่อนเปิดใช้งานจริง ไม่ใช่งานเสริม** (ดู §1.3: ปัจจุบันไม่มีเลย) ต้องจำกัด**ต่อชื่อผู้ใช้**และต่อ IP แยกกัน, ไม่ใช้บัคเก็ต `anonymous` ร่วม (ไม่งั้นคนเดียวล็อกทุกคนออกได้), และ**ไม่เชื่อ `x-forwarded-for`** ตามที่ middleware เดิมระบุไว้ว่าปลอมได้ — ข้อนี้ต้องออกแบบให้ดี เพราะหลังเครื่อง PM2 อาจมี reverse proxy ที่ทำให้ IP จริงหายไป (ต้องตรวจโครงสร้างจริงก่อน) ตัวจำกัดแบบในหน่วยความจำใช้ได้เฉพาะรันโปรเซสเดียว ถ้าจะรันหลายตัวต้องใช้ที่เก็บร่วม
  ความเสี่ยงเพิ่มของ AD: หาก AD ตั้ง account lockout policy ไว้ (**ยังไม่ได้ตรวจนโยบายนี้**) การเดาผิดซ้ำผ่านแอปจะล็อกบัญชีโดเมนของพนักงานจริงทั้งหมด ไม่ใช่แค่ในแอปนี้ — ต้องถามผู้ดูแล AD ว่าเกณฑ์คืออะไร แล้วตั้งเพดานการลองของแอปให้ต่ำกว่าเกณฑ์นั้น
- [ ] unit test ส่วน `lib/ad.ts` ด้วย LDAP จำลอง (ไม่ต่อ DC จริงใน CI)

### ระยะ 2 — สร้างบัญชีและซิงก์ข้อมูล
- [ ] ตามข้อ 1 ของ §3: สร้างบัญชีตอนล็อกอินครั้งแรกจาก AD (ชื่อ, อีเมลจาก `mail`, ตำแหน่ง, แผนกที่จับคู่ได้) เป็นบทบาทต่ำสุด **ห้ามได้สิทธิ์อนุมัติโดยอัตโนมัติ**; Admin กำหนดบทบาทที่หน้าผู้ใช้
- [ ] จับคู่ `department` (ข้อความ) กับตาราง `Department`: ถ้าจับไม่ได้ให้ปล่อยว่างและแจ้ง Admin ไม่เดา เพราะแผนกกำหนดสิทธิ์อนุมัติ (`filterByDepartment`) — แผนกผิด = ผู้อนุมัติผิดคน
- [ ] ซิงก์ชื่อ/อีเมล/ตำแหน่งทุกครั้งที่ล็อกอิน (AD เป็นแหล่งจริง) แต่ **ไม่เขียนทับบทบาทและแผนกที่ Admin ตั้งไว้**
- [ ] ปรับหน้า admin users: บัญชี `AD` ซ่อนช่องรหัสผ่านและปุ่มรีเซ็ต; ปุ่ม "สร้างผู้ใช้" รองรับเลือกจาก AD (ค้นหาด้วยชื่อ) แทนการกรอกรหัสผ่าน
- [ ] `change-password` และ `reset-password`: **ปฏิเสธบัญชี `AD` ที่ฝั่งเซิร์ฟเวอร์** (ไม่ใช่แค่ซ่อนปุ่ม) ด้วยข้อความชี้ไปเปลี่ยนที่ระบบโดเมน

### ระยะ 3 — ทางเข้าฉุกเฉิน, ทดสอบ, และเอกสาร
- [ ] ทางเข้าแบบ `LOCAL` สำหรับ Admin ฉุกเฉิน: จำกัดจำนวน, รหัสผ่านยาว, เก็บในที่ปลอดภัย, ตรวจ audit; ทดสอบจริงว่าเข้าได้ขณะ AD ไม่ตอบ
- [ ] E2E: คงบัญชี `e2e_*` เป็น `LOCAL` (ชุดเดิม 37 ข้อต้องยังผ่านโดยไม่แก้เมื่อปิดโหมด AD) แล้ว**เพิ่มเคสใหม่**: ล็อกอิน AD สำเร็จ/รหัสผิด/บัญชีถูกปิด/ไม่อยู่ในกลุ่ม/AD ไม่ตอบ/สร้างบัญชีครั้งแรก/ผู้ใช้ AD เปลี่ยนรหัสผ่านในแอปไม่ได้ — ต้องมี LDAP จำลองหรือบัญชีทดสอบใน AD จริงที่ได้รับอนุญาต
- [ ] ทดสอบกับบัญชี AD จริงอย่างน้อย: ปกติ, รหัสผ่านหมดอายุ, บัญชีถูกล็อก, บัญชีปิด, ชื่อที่มีอักขระไทย/เว้นวรรค, คนอยู่หลายกลุ่ม
- [ ] ปรับ `.env.example`, `README`, `CLAUDE.md`, runbook, คู่มือผู้ใช้ ("รหัสผ่านเดียวกับที่ใช้เข้าคอมพิวเตอร์")

### ระยะ 4 — เปิดใช้งานทีละขั้น
- [ ] เปิดโหมด AD ให้กลุ่มนำร่อง (เช่น IT) ก่อน ทั้งที่ยังเก็บล็อกอินเดิมไว้ → ขยายทีละแผนก → ปิดล็อกอิน local ของผู้ใช้ทั่วไป (คงไว้เฉพาะบัญชีภายใน)
- [ ] แผนย้อนกลับ: ปิดด้วย env กลับเป็น `LOCAL` ได้ทันทีโดยไม่ต้องแก้ข้อมูล (เพราะเพิ่มคอลัมน์ไม่ได้ลบอะไร และรหัสผ่าน bcrypt เดิมของบัญชี `LOCAL` ยังอยู่) — **ข้อจำกัด:** บัญชีที่สร้างจาก AD จะไม่มีรหัสผ่าน local ย้อนกลับแล้วเข้าไม่ได้จนกว่า Admin จะตั้งรหัสให้
- [ ] เฝ้าดู: อัตราล็อกอินล้มเหลว, เวลาตอบของ DC, บัญชี AD ถูกล็อกจากการลองของแอป

## 5. ความเสี่ยงและสิ่งที่ยังไม่ทราบ

| ความเสี่ยง | ระดับ | การรับมือ |
|---|---|---|
| ไม่มี rate limit ที่จุดล็อกอิน (มีอยู่แล้วตอนนี้) → เดารหัสผ่านโดเมนได้ไม่จำกัด และอาจ**ล็อกบัญชีโดเมนของพนักงาน** (ถ้า AD เปิด lockout policy — ยังไม่ได้ตรวจ) | **สูง** | ทำเป็นเงื่อนไขก่อนเปิดใช้ (ระยะ 1), จำกัดต่อชื่อผู้ใช้+IP แยกกัน, ถามเกณฑ์ lockout จากผู้ดูแล AD, พิจารณาดีเลย์แบบเพิ่มขึ้น |
| แอปจัดการรหัสผ่านโดเมนแบบ plaintext ผ่านหน่วยความจำ | กลาง | LDAPS เท่านั้น, ไม่ log, ไม่เก็บ, ตรวจโค้ด |
| อีเมลแจ้งอนุมัติส่งผิดที่อยู่ถ้าใช้ UPN แทน `mail` | กลาง | ใช้ `mail` เท่านั้น; ผู้ใช้ที่ไม่มี `mail` → ไม่ให้เข้าหรือแจ้ง Admin (ข้อ 6 §3) |
| จับคู่แผนกผิด → ผู้อนุมัติผิดคน | กลาง | ไม่เดา, ว่างไว้และให้ Admin กำหนด |
| DC ล่ม/เครือข่ายขาด → ทุกคนเข้าไม่ได้ | กลาง | failover 2 DC, timeout สั้น, ทางเข้าฉุกเฉิน local |
| ชุด E2E พังเมื่อเปลี่ยนล็อกอิน | กลาง | คงบัญชี `e2e_*` เป็น LOCAL, ทดสอบก่อนเปิดโหมด AD |
| ผู้ใช้ที่ AD ปิดแล้วแต่เซสชัน JWT ยังใช้ได้ถึง 8 ชม. | ต่ำ-กลาง | ปัจจุบันตรวจ `isActive` ใน DB ต่อ request แต่นั่นคือสถานะ**ในแอป** ไม่ใช่ AD — ถ้าต้องการให้ AD ปิดมีผลทันที ต้องเพิ่มการตรวจสถานะ AD เป็นระยะ (งานเพิ่ม ควรตัดสินใจ) |
| **ไม่ทราบ:** สภาพข้อมูล AD ของผู้ใช้ทั้งหมด, นโยบายความปลอดภัยฝั่ง DC, ฐาน production, ผู้ใช้จริงและรูปแบบชื่อผู้ใช้ | — | ระยะ 0 |

## 6. ขอบเขตที่ **ไม่รวม** ในแผนนี้
- SSO อัตโนมัติ (Kerberos/Windows Integrated) และ Entra ID/OIDC — เป็นโครงการแยก
- การซิงก์รายชื่อ/ปิดบัญชีอัตโนมัติจาก AD ตามเวลา (ระยะ 2 ซิงก์เฉพาะตอนล็อกอิน)
- ยกเลิกคอลัมน์ `password` — คงไว้เพื่อบัญชี `LOCAL`

## 7. ประมาณงาน (หยาบ และขึ้นกับคำตอบ §3)
ระยะ 1–2 ราว 4–6 วันทำงานรวมทดสอบกับ DC จริง, ระยะ 3 อีก 2–3 วัน, ระยะ 0 และ 4 ขึ้นกับผู้ดูแล AD/เครือข่ายมากกว่าการเขียนโค้ด **ตัวเลขนี้เป็นการประมาณ ไม่ได้อิงการทดลอง** — ความไม่แน่นอนหลักคือไลบรารี LDAP กับ DC ของคุณ และนโยบาย signing
